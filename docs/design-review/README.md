# Design review — Enable Banking and budgeting across currencies

An inventory of design, encapsulation and SOLID problems in the code written for the Enable Banking integration and budgeting across currencies (`git diff b0dcef9..` at the time), and what was done about each.

## How it was done

An orchestrated workflow:

1. **Inventory.** Four reviewers, one per area, read only the code of this work and reported concrete problems with file and line evidence and the smallest fix.
2. **Triage.** One reviewer checked every finding against the code and tried to refute it: wrong evidence, a deliberate documented decision, a duplicate, or a fix that costs more than it buys. It grouped the rest into packages that touch disjoint files.
3. **Fix.** One agent per package, keeping behavior and the HTTP contract unchanged except where the finding was that behavior contradicted a decision. Tests go through each module's interface.
4. **Verify.** Type checks, unit tests, client and demo builds, Prettier and the full e2e suite, plus a review of the combined diff.

**Result:** 42 findings, 35 fixed and 7 skipped.

## Where the fixes landed

There's no separate design-review change: each fix was folded into the functional block whose
code it touches, and is described there as part of that block.

- **Enable Banking** (bank sync, account currencies, bank-sync core): BANK-2 and BANK-6 (the
  first `accountService`), BANK-3 (the same-currency rule in pure matching), BANK-4, BANK-5,
  BANK-7, BANK-8, BANK-9, UI-10, UI-11 (with Escape closing only the topmost dialog).
- **Exchanges, boundary transfers and recurring matching**: BANK-3 (`exchangeSiblings`),
  BANK-7 (the recurring count), TX-1, TX-2, TX-6, TX-8, TX-9, TX-11, UI-4 (without the
  currencies), UI-5, UI-8 (`canLinkAsTransfer`).
- **Budgeting across currencies**: BANK-1, BANK-2 (M1/M2 rules), FX-1, FX-2, FX-4, FX-5, FX-6,
  FX-8, FX-9, TX-3, TX-4, TX-5, UI-1, UI-2, UI-3, UI-4 (the currencies), UI-7, UI-8
  (`budgetValueEditable`), UI-9, and the repairs found while verifying (savepoints in the demo,
  the `CurrencyInput` race).

## BANK — Bank-sync core and Enable Banking

- **BANK-1** (high, duplication): Account mapping still takes the budget currency from the client, though M2 moved it to the server. **Fixed:** The server now decides the budget currency. `budgetCurrency` is gone from `mappingSchema`, so Zod drops it when an older client still sends it. `service.mapAccounts(connectionId, requests)` reads it through a new optional `EnableBankingServiceDeps.budgetCurrency`, which defaults to `budgetCurrency()` from fx/settings. When none is set it throws `ConflictError('Choose the budget’s currency first.')`, which `sendError` already maps to 409. Tests: a request with a stale `budgetCurrency: 'USD'` in a EUR budget now creates the EUR bank account with `currency: null` and on budget (this failed before the change). A service with `budgetCurrency: () => null` refuses to map accounts.
- **BANK-2** (medium, duplication): Creating an account is a second copy of POST /api/accounts, and the copies already differ. **Fixed:** New `services/accountService.ts` has `createAccount(input)`. It applies the new-account defaults, normalizes the currency with `storedCurrency(c, budgetCurrency())` when the budget has one, sets the start-off-budget rule, inserts the row and calls `scheduleRatesDownload()` for an account in another currency. It opens no transaction of its own. POST /api/accounts and `applyMappings` (inside its existing `db.transaction`) both use it, so accounts created from the bank now also schedule the rates download.
- **BANK-3** (medium, layering): Transfer and exchange pairing rules are split across SQL, the orchestrator and the pure module. **Fixed:** `TransferCandidate` and `TransferQuery` now carry `currency` (stored, null = the budget's). `pickTransferCounterpart` filters `c.currency === query.currency`, with a comment pointing to `sameCurrency` in utils/transferRules.ts. The `ImportStore` interface gains `storedCurrency(accountId)`. `transferCandidates` dropped the SQL `is` currency clause and returns each candidate's currency. The exchange sibling count moved into a pure `exchangeSiblings(here, id, amount, currency, partners)` in matching.ts, so `importTransactions` only wires the calls. Property tests: a different currency is never paired, even when the bank names the account; `exchangeSiblings` counts only same-direction rows that look like an exchange, never the transaction itself. New import case: an opposite amount in a GBP account named by IBAN is not linked.
- **BANK-4** (medium, dependency-inversion): 'Today' comes from the injected clock in two different ways (UTC and local), and the clock is only partly injected. **Fixed:** Added `localDay(nowMs)` (date-fns `format`, local time) in rules.ts, used by both `service.mapAccounts` (which used the UTC `toISOString().slice(0,10)`) and `syncService`. `saveConfig`, `insertConnection` and `bindAccounts` in the store take an `at` timestamp, and `service.configure` passes `new Date(now()).toISOString()`.
- **BANK-5** (medium, purity): Pure mapping and sync-window rules live inside modules that import the database. **Fixed:** New pure `services/enableBanking/rules.ts` (no db, no clock) holds `DEFAULT_HISTORY_DAYS`, `BACKGROUND_SYNC_INTERVAL_MS`, `RESYNC_OVERLAP_DAYS`, `localDay`, `defaultSyncFrom`, `syncFromAfter`, `planMapping` with `MappingRequest`/`MappingPlan`/`TargetSide`, and `syncWindowStart`, whose fallback now calls `defaultSyncFrom(today)`. It also adds `shouldSkipBackgroundSync(lastSyncedAt, nowMs)` and `consentEnded(validUntil, nowMs)`. accountMapping.ts keeps only `applyMappings` and its DB helpers; syncService uses the new checks. rules.test.ts imports only `./rules.js` and has new property tests: the 6-hour boundary, consent end, `syncWindowStart(null, null, d) === defaultSyncFrom(d)`, and `localDay`.
- **BANK-6** (medium, layering): The adapter reads and writes the accounts table from three modules, bypassing its own store. **Fixed:** accountService adds `accountBalance(id)`, `setBalanceTo(id, cents)` (the D7 opening balance), `openAccount(id)` and `accountSummary(id)`, which ignores closedAt so a closed account still shows its name and balance as before. Users: `withBalance` in routes/accounts.ts, `accountView` in service.ts, and syncService (the closed-account check and opening balance). service.ts and syncService.ts no longer import `db` or `accounts`.
- **BANK-7** (low, duplication): SyncResult copies ImportResult's counters by hand, so skipped other-currency transactions disappear. **Fixed:** `SyncResult` is now `Pick<ImportResult, added|matched|transfers|recurring>` plus the connection fields, with the same JSON fields as before. A single `COUNTS` list drives the exported `emptySyncResult(connection, status)` and the pure `addCounts(result, imported)`, used by `runSync` and by `syncAll`'s catch. When `imported.otherCurrency > 0`, it logs `n transaction(s) in another currency skipped in <bank.id>` through `logError`. Covered by the new syncService.test.ts property test.
- **BANK-8** (low, coupling): The route imports a generic text sanitizer from the provider's JSON-mapping module. **Fixed:** `cleanText` moved verbatim to `server/src/utils/text.ts`, and its property test moved from mapping.test.ts to utils/text.test.ts. routes/enableBanking.ts, mapping.ts and rules.ts import it from there.
- **BANK-9** (low, interface-segregation): The ConsentRegistry interface has a method only a test uses, and lacks a binding the service needs. **Fixed:** Removed `info()` from `ConsentRegistry` and its implementation. The test now checks the stored info through `complete`'s `finish(info)` callback. `fail(state, error, expectedId?)` uses `live(state, expectedId)`, and `completeFromAddress` passes `id`. When `fail` returns false while the user's consent is still pending, it throws the same 'another or an expired attempt' ConfigurationError. If the consent already finished (the same address pasted twice), it still returns that outcome. New test: a fail with another consent's id leaves both consents untouched, and both can still finish.

## FX — Budget currency, exchange rates, budget and reports

- **FX-1** (medium, dependency-inversion): The 'demo never downloads rates' rule (M10) is only enforced in the currencies router; other callers use the real downloader through a module-global. **Fixed:** download.ts now owns the rule 'may this installation download rates'. Its options are `{ fetch: typeof fetch | null; today; now }`. With `fetch: null`, `downloadRates()` resolves `{downloaded:0,error:null,unsupported:[]}` without reading or writing settings, and `scheduleRatesDownload()` does nothing. New export `ratesDownloadAvailable()`. `ratesUpdatedAt` comes from `options.now()`. In routes/currencies.ts, `CurrenciesDeps` is gone: `createCurrenciesRouter()` takes no arguments, returns the same 403 NOT_HERE when `!ratesDownloadAvailable()`, and calls `scheduleRatesDownload`/`downloadRates` directly. browser/app.ts calls `configureRatesDownload({ fetch: null })` once when the module loads, with a comment citing M10. index.ts mounts `createCurrenciesRouter()`. As a result, accounts.ts, ruleService.ts and any new caller can't download in the demo, even after restoring a backup with download_rates = 1. budgetAcrossCurrencies.test.ts: the demo case runs through an `asInDemo` helper (fetch null, restored in `finally`). A new test restores a backup with downloadRates=1 using fetch null over a throwing spy, then adds an account and a transaction in NOK. It asserts the spy is never called, `downloadRates()` returns the empty result, and ratesUpdatedAt/ratesError stay the same. I checked that this test and the 403 test fail if `fetch: null` is ignored.
- **FX-2** (medium, purity): The typed budget amount is validated against the stored row before the update and applied after it, and the second check's result is ignored. **Fixed:** conversion.ts has two new pure functions: `budgetAmountProblem(row, budgetAmount)`, with the same messages in the same order, and `exchangeOtherAmount(other, foreign)`. refreshFx uses `exchangeOtherAmount` instead of the inline check, and checkBudgetAmount uses the same helper to decide `exchangeIntoBudget`. In fxService, checkBudgetAmount and setBudgetAmount keep their signatures. Both read the transaction as it is now through one private `budgetAmountRow(id)` and apply `budgetAmountProblem`. setBudgetAmount now uses the row it checked (no second read) and returns the outcome. No transaction wrapper was added inside setBudgetAmount: in the demo that would make refreshFx nest (see notFixed). New property tests in conversion.test.ts cover: any same-direction non-zero amount is accepted; the other direction and zero (on either side) are refused; the order of checks over all flag combinations; null always allowed unless not foreign or a split part; and exchangeOtherAmount. `FxOutcome` became `FxOutcome<T extends object = object>`. Plain `FxOutcome` is unchanged for existing callers.
- **FX-3** (medium, interface-segregation): Each inserted transaction is converted on its own, so bulk imports reload the currency pair's full rate history once per row. **Skipped:** Duplicate of TX-4 (same code path, same fix).
- **FX-4** (medium, duplication): Valuing a balance in another currency (M6) is written twice; the net-worth route bypasses fxService and reads the rate store directly. **Fixed:** fxService has a new `latestRates()`: a finder for one request that reads the budget currency once and each pair once (cache shared with refreshFx through a private `ratesTo(budget)`). New `balanceValuer()` returns `(currency, balance, date) => { value, asOf } | null` using latestRateOn + convertCents. `latestRate(currency, date)` keeps its shape and is now `latestRates()(currency, date)`. The reports.ts net-worth loop uses `balanceValuer()` and no longer imports conversion, ratesStore or settings. The currencies overview uses one `latestRates()` per request instead of `latestRate` per currency. netWorth.test.ts and reports.test.ts pass unchanged.
- **FX-5** (medium, encapsulation): The accounts API doesn't enforce 'null = the budget's currency'; only Enable Banking normalizes it. **Fixed:** `createAccount` and `updateAccount` normalize currency with `storedCurrency(c, budgetCurrency())` whenever the budget has a currency (update only when the key is sent). POST and PUT /api/accounts with the budget's own currency now store null. New HTTP tests in accountCurrency.test.ts and property tests in accountService.test.ts.
- **FX-6** (medium, layering): PUT /accounts/:id runs a multi-step business write in the route, not atomically. **Fixed:** `updateAccount(id, changes)` in accountService now owns the sequence: update the row, call `uncategorizeTransfersThatStopCrossing` when isOffBudget changed (M8), and call `refreshFx({accountIds})` plus `scheduleRatesDownload()` when the currency changed (M3). It returns `{account, transfersUncategorized}` or null. The PUT route only validates and calls it; its response is the same `{...withBalance(account), transfersUncategorized}`. Tests: moving an account off budget uncategorizes a boundary transfer; a currency change converts its transactions at a typed-in rate. It is not wrapped in one transaction yet; see notFixed.
- **FX-7** (low, duplication): 'Has no value in the budget currency' is restated by hand in several places instead of reusing budgetValue/hasBudgetValue. **Skipped:** Not worth its code. `accounts.currency is not null and fx_rate is null` is equivalent to `budgetValue is null` once FX-5 enforces null=budget currency. Swapping in budgetValue adds a per-row subquery to budget.ts and the waiting counts for no behavior gain.
- **FX-8** (low, encapsulation): Manual rate writes are split across the route and the store: the route builds storage ids, applies currency rules and must remember to re-convert. **Fixed:** fxService has `setManualRate(code, date, rate): FxOutcome<{ rate: ManualRate }>`: 409 'Choose the budget’s currency first', 400 'That’s the budget’s own currency', otherwise it saves and calls refreshFx({currency}). It also has `removeManualRate(code, date): FxOutcome`, with 400 'Invalid request' when there is no budget currency (as the route had), 404 'No rate typed in for that date', otherwise it deletes and calls refreshFx. ratesStore's `deleteManualRate(base, quote, date): boolean` builds the id itself, so `rateId` no longer appears in the route. The PUT and DELETE rate routes only validate and map the outcome, with the same responses. download.ts keeps its own save + refreshFx for downloaded rates. backup.test.ts now mounts `createCurrenciesRouter()` and sets up the budget currency and rates with `PUT /currencies` and `PUT /currencies/GBP/rates/...`, asserting 200, instead of `saveBudgetSettings`/`saveManualRate`.
- **FX-9** (low, encapsulation): Deciding which tables a restore keeps requires the route to pass the raw body to two backupService functions. **Fixed:** `parseBackup(input)` returns `{ tables, keep }`; it works out `keep` (ADDED_FOR_CURRENCIES tables missing from the body). The exported `tablesToKeep` is removed. `restoreBackup(parsed)` keeps those tables, returns the same `restored` counts, and calls `refreshFx('all')` itself after its transaction commits. routes/export.ts is now parse → saveSafetyCopy → restoreBackup, with the same responses and error handling. backup.test.ts passes, including the old backup keeping the budget currency and rates.
- **FX-10** (low, coupling): The download error is a string encoding shared by storage, the API and two client parsers. **Skipped:** The fix changes the documented HTTP contract (docs/multi-currency/api.md: ratesError is null, "unreachable" or "unsupported:ARS,KES"), and no decision is contradicted. The duplicated client parser is fixed by UI-9.

## TX — Transactions, transfers and recurring matching

- **TX-1** (medium, duplication): PUT /transactions/:id re-implements part of the transfer-pair rule instead of using transferPairProblem, and the copy has already drifted. **Fixed:** updateTransferSide checks the pair as it will be after the edit: transferPairProblem({amount, account: self}, {amount: mirrored ?? other.amount, account: other}), but only when the amount changes, so a notes or date edit never gets blocked by old data. The hand-written sign check is deleted. Bug fix: PUT {amount: 0} on a same-currency transfer now returns 400 'A transfer takes money out of one account and puts it into the other' and changes nothing, including a date sent with it; it used to write 0/0. A sign flip on an exchange now returns the same message. Tests added in transferLinks.test.ts.
- **TX-2** (medium, layering): Transfer writes are split between the route (create, mirror edits) and transactionHelpers (link, unlink), each with its own copy of the pair's shape. **Fixed:** transactionHelpers now has one loader, transferAccount(tx, id), returning {id, name, currency, isOffBudget}, plus transferPayeeName(account). linkTransferRows, uncategorizeTransfersThatStopCrossing (shared column shape) and the new functions all use them. createTransfer(input) holds what was POST /transfer's body: 404 'Account not found', the amount received, a transferPairProblem check, the category side via sideTakesCategory, both inserts in one db.transaction, then afterTransactionsWritten. The route keeps the alreadyCreated idempotency check and returns 201 with the same JSON. updateTransferSide(tx, existing, edit) loads the pair, checks the edit and writes the other side's date and mirrored amount. The route-local transferPair is gone. One deviation from the brief: 'Transfers stay in their accounts' and the category-on-a-non-boundary-side check also moved into updateTransferSide, so the route keeps no transfer rules and only maps the outcome. Same messages and 400s; the account move uses reason invalid_pair, the category uses no_category.
- **TX-3** (medium, dependency-inversion): insertNewTransaction calls the rate download directly, bypassing the injected scheduler (M10 demo) and the M4 placement; other creation paths never trigger it. **Fixed:** New /home/user/fly-budget/server/src/services/transactionFx.ts exports afterTransactionsWritten(ids). It runs convertTransactions(ids), then checks whether any of the rows still waits for a rate (waitsForRate for one id, one chunked join query for many) and if so calls scheduleRatesDownload(). The demo guard is now inside download.ts (fx package, configureRatesDownload({fetch: null})), so this is a no-op in the demo. It replaces the bare convertTransactions calls after creating transactions in five places: the split POST, createTransfer (POST /transfer), mark-paid in routes/schedules.ts, autoCreateDueScheduled (now batched into one call at the end) and insertNewTransaction. ruleService no longer imports download.ts or waitsForRate. Rule-apply splits stay convert-only.
- **TX-4** (medium, single-responsibility): insertNewTransaction converts one row at a time, defeating the batch mode that CSV import and bank sync rely on. **Fixed:** InsertOptions (now exported) has `deferFx?: boolean`. When it is set, insertNewTransaction skips the FX step; single-row calls behave as before. CSV /import/confirm passes deferFx: true, collects the inserted ids and calls afterTransactionsWritten(ids) once inside the same db.transaction. The response is still {imported, skipped}. Tested in budgetAmountEdits.test.ts: a CSV import into a GBP account with a typed-in rate converts every row (fxRate 1.2, fxSource 'rate'), and with downloading on, the import itself starts a download for rows that have no rate.
- **TX-5** (medium, encapsulation): budgetAmount is validated against the row before the edit and written after the commit, and the write's result is ignored. **Fixed:** PUT /transactions/:id no longer calls checkBudgetAmount before the edit. Inside its db.transaction, after the transfer, row and children updates, it runs convertTransactions([id]) and then setBudgetAmount(id, budgetAmount). A refusal (or a transfer refusal) throws a local EditRefused(status, message), which rolls everything back; it is caught outside and answered with that status and error. New budgetAmountEdits.test.ts covers three cases. {amount: 500, budgetAmount: 400} on a -500 GBP row now succeeds with fxSource 'manual' (it used to be refused). {accountId: <EUR account>, budgetAmount: 4500} returns 400 'This account is in the budget’s currency' and the account is unchanged (it used to be 200 with the value silently dropped). {amount: 500, budgetAmount: -400} returns 400 and the amount is unchanged.
- **TX-6** (low, duplication): The rule for which transactions can be linked as a transfer is written twice, and the candidate search lives in the route. **Fixed:** utils/transferRules.ts gains three things. linkableProblem(t) is pure and uses the same messages and reasons as before; linkTransferRows now uses it. rankTransferCandidates(source, nearby) is pure: it drops rows that can't be linked or wouldn't make a valid pair, sorts closest date first then by id, and keeps the top MAX_TRANSFER_CANDIDATES (20). TRANSFER_CANDIDATE_DAYS moved there too. transferCandidates(id) in transactionHelpers keeps the SQL prefilter (other open accounts, ±7 days) and returns null for a missing id (the route answers 404). It returns [] when the source row can't be linked; the zero-amount case is left to transferPairProblem, with the same result. Response fields are unchanged. Added property tests for linkableProblem and rankTransferCandidates, and HTTP tests: a split parent, a split part or a reconciled source gets [], a reconciled candidate is never offered, an unknown id gets 404, and the exact response fields are checked.
- **TX-7** (low, duplication): GET /transactions computes each row's budget value in JS instead of selecting the SQL budgetValue that every total uses. **Skipped:** Changes the documented response (api.md: only rows in accounts in another currency have budgetAmount) and adds a per-row subquery. convertCents is explicitly written to match SQLite round(), so the two cannot disagree today.
- **TX-8** (low, coupling): scoreMatch spots a 'loose' variable amount by comparing score values, and getMatchSuggestions keeps its own copy of the direction rule. **Fixed:** amountScore became amountFit(type, amount, expected), returning 'exact' | 'close' | 'loose' | null; points come from an AMOUNT_POINTS map (30/20/10), so every score is the same as before. scoreMatch rejects `fit === 'loose' && payeeScore === 0` without comparing against a score constant. In pickImportMatches I removed the `p.amountScore > 0` check, since a score above 0 already implies an amount fit. In getMatchSuggestions I removed the direction pre-filter on schedule.amount, so only amountFit against occ.expectedAmount decides direction. The score is now computed before the per-transaction dismissal query, which keeps that query from running for transactions in the wrong direction. New property tests in scheduleMatching.test.ts cover the fit boundaries in both directions, 'a loose amount needs the payee or bank text', and 'a closer amount never scores lower'. A new HTTP test in scheduleMatchText.test.ts checks that after an item's sign is flipped, last week's occurrence is still suggested its matching transaction.
- **TX-9** (low, duplication): autoMatchImported hard-codes the 14-day maximum date flexibility that the schedules route defines. **Fixed:** scheduleMatching.ts exports MAX_DATE_FLEXIBILITY = 14. routes/schedules.ts uses it in the dateFlexibility schema, and matchingEngine.autoMatchImported uses it for its window, replacing the literal 14 and its comment. An HTTP test checks that MAX is accepted and MAX+1 is refused.
- **TX-10** (low, duplication): Client and server each keep their own copy of the transfer rules. **Skipped:** A deliberate repo pattern: account types are kept as synced copies too, and the client header points at the server. Importing server/src into the client's tsc build outside the demo worker is a riskier build change than the drift it prevents.
- **TX-11** (low, layering): Transfer services return HTTP status codes instead of domain reasons. **Fixed:** TransferOutcome is now `{ok:true} | {ok:false; reason: TransferRefusal; error}`, where TransferRefusal is 'not_found' | 'not_plain' | 'reconciled' | 'not_a_transfer' | 'invalid_pair' | 'no_category'. I added 'no_category' for a category on a side that can't take one. A route-side transferStatus(reason) maps not_found to 404, reconciled to 403 and the rest to 400, so link-transfer and unlink-transfer answer with the same statuses and messages as before. linkTransfer(...).ok still works for importStore. The transferLinks tests now assert reasons, plus the HTTP statuses.

## UI — Client

- **UI-1** (high, duplication): Enable Banking mapping still forces foreign accounts off budget (D11), contradicting M1; the 'starts off budget' rule exists in three client copies. **Fixed:** Added a pure `startsOffBudget(type, foreign)` to utils/accountTypes.ts, with fast-check tests in the new utils/accountTypes.test.ts. AddAccountModal (type and currency changes) and enablebanking/model.ts (the starting row) use it, and so does the mapping form when the type changes; model.defaultOffBudget is removed. mappingAction now sends `row.offBudget` as it is and no longer takes the unused `budget` argument. In the mapping form the Off budget box can be changed for foreign accounts, and its text is now ForeignBudgetHint. The model test is now 'starts off budget for another currency, and can be put on budget', plus a property test that the box is sent unchanged.
- **UI-2** (medium, layering): Account mapping sends the client's budget currency to the server after M2 moved it into the budget. **Fixed:** Removed `budgetCurrency` from mapEnableBankingAccounts(connectionId, accounts) and from useMapEnableBankingAccounts. The mapping form uses useBudgetCurrency() only for display and defaults. The e2e test no longer expects budgetCurrency and asserts `expect(mapping).not.toHaveProperty('budgetCurrency')`. - **UI-3** (medium, purity): utils/budgetCurrency.ts mixes pure helpers with a React Query hook, which makes the 'pure' Enable Banking model impure and forced a window guard into api/base.ts. **Fixed:** I moved useBudgetCurrency to the new client/src/hooks/useBudgetCurrency.ts (same body) and updated all 11 importers. utils/budgetCurrency.ts now imports no hooks, stores or API modules. api/base.ts is back to `window.__API_BASE__ ?? '/api'` without the guard, and every unit test still loads in Node.
- **UI-4** (medium, duplication): Which cached queries a conversion-affecting write refreshes is hand-listed in six places, and the lists have drifted. **Fixed:** New hooks/budgetFigures.ts with refreshBudgetFigures(qc) (accounts, transactions, budget, budget-summary, category-history, reports, dashboards, goals, currencies) and refreshRecurring(qc) (schedules, schedule-occurrences, schedule-summary, match-suggestions). Money leaves the side with the negative amount; `amount` is the sending side's; `toAmount` is sent only for an exchange; `categoryId` only across the budget boundary. It has property tests. - **UI-6** (medium, coupling): Rows don't carry their account's currency, so every screen re-joins against the open-accounts list and closed accounts fall back to the budget symbol. **Skipped:** The fix adds fields to three server responses (transactions, occurrences, match suggestions) plus client changes across eight components. - **UI-7** (low, duplication): The exchange-rate text '1 X = r Y' is implemented three times with different precision, and two exported rateText functions take their arguments in opposite orders. **Fixed:** There is now one rateText(base, quote, rate), in currencyRates.ts. fxDisplay's own rateText is gone; fxNote calls the shared one and still leaves the rate out when it's missing or invalid. exchangeLabel uses it too, and exchangeRate() returns the unrounded |to|/|from| (null only when an amount is 0). The format shows at least four decimals and at least six significant digits: 1.1000, 1.17981, 0.00612345, 0.000058. Pure 6-significant-digit formatting would have broken e2e/tests/currencies.spec.ts:74 ('1 EUR = 1.1000 USD'), which I may not edit. Tests now cover an IDR to EUR rate around 0.000058 in all three test files.
- **UI-8** (low, single-responsibility): TransactionDetailPanel re-implements server eligibility rules inline (Link as transfer, editable budget value). **Fixed:** Added `canLinkAsTransfer(tx)` to utils/transfers.ts (comment points to linkableProblem and linkTransfer on the server) and `budgetValueEditable(tx)` to utils/fxDisplay.ts (comment points to budgetAmountProblem and checkBudgetAmount), each with property tests. TransactionDetailPanel uses them instead of the inline rules (valueLocked = !budgetValueEditable(tx)).

- **UI-10** (low, purity): Enable Banking's flow logic (consent and mapping steps, renewal, access warnings) sits in components while model.ts claims to hold the screen rules. **Fixed:** Added pure functions to enablebanking/model.ts, with tests: accessStatus(connection, now) returns daysLeft, expired, expiresSoon, renewNeeded and the access text; accountsToMapAfterConsent(accounts, renewing); stepAfterConsent(count, renewing); stepAfterMapping(result, renewing).
